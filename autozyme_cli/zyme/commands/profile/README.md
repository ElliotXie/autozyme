# `zyme profile` — multi-backend profiling for autozyme tasks

Profile a single pipeline run, emit structured evidence (top-N hotspots,
per-override timing, normalized JSON) so an agent can decide where to
optimize next. Diagnostic only: never writes `results.tsv`, never commits,
never runs `evaluate`.

```
zyme profile [hypothesis] [--backend full|cpu|mem|native]
             [--dataset TIER] [--no-archive] [--json]
             [--diff A --diff-against B]
```

---

## TL;DR

```bash
zyme profile                              # default: backend=full (Scalene/profvis)
zyme profile --backend native             # macOS sample(1), sees BLAS/Cython/Rcpp
zyme profile --backend mem                # memray (py) / Rprof+memory (R)
zyme profile --backend cpu                # cProfile / Rprof — fallback / call-counts

zyme profile --json | jq .hotspots        # machine-readable
zyme profile --diff history:cpu_tiny \
             --diff-against current       # cross-iteration delta
```

Outputs:
- `profile_history/<run-id>/profile.json` — canonical, normalized schema
  (agent reads this)
- `profile_history/<run-id>/<backend-native-artifact>` — raw
  (`profile.out` / `Rprof.out` / `scalene.json` / `memray.bin` /
  `native_sample_*.txt`)
- `profile_history/<run-id>/run.log` — pipeline stdout/stderr used to
  extract totals and override timing
- `--no-archive` writes overwritten scratch output to `profile_history/current/`

## The four backends

| backend  | Python                | R                          | Install            | Default? |
|----------|-----------------------|----------------------------|--------------------|----------|
| `cpu`    | cProfile              | Rprof                      | stdlib             | fallback |
| `full`   | Scalene               | profvis (+Rprof)           | optional           | ✅ default |
| `mem`    | memray scoped or whole-process | Rprof + memory.profiling | optional (memray)  |          |
| `native` | macOS `sample(1)`     | macOS `sample(1)`          | macOS only         |          |

**Pick by question:**

- "Where's the hot path?" → **`full`** (Scalene's line-level python/native
  split is the most agent-readable). Fallback to `cpu` if Scalene unavailable.
- "Where's the memory pressure?" → **`mem`**. memray sees NumPy/torch
  native buffers tracemalloc misses. Python tasks that expose a
  `with_profile()` region get scoped memray; older tasks without one fall
  back to whole-process memray.
- "What C function inside `np.linalg.svd` / `fgseaMultilevel` is slow?"
  → **`native`**. Only backend that sees inside Rcpp / Cython / OpenBLAS.
- "Did my override actually run? How many times?" → any backend; read the
  **Override timing** section of the output (see below).

**Fallback rules:**
- `full` falls back to `cpu` when Scalene/profvis are missing (with install hint).
- `mem` and `native` REFUSE to fall back — they're a different signal axis;
  silent substitution would mislead.

## Override timing — autozyme's deterministic side-channel

Every invocation surfaces `override_summary` in `profile.json`, regardless
of backend. This is generated by `install_override` itself — a per-call
timer wrapped around the patched function. Reaches the runner via
`[override summary]` lines on stdout:

```
[override summary] fgsea::fgseaMultilevel pid=87412 calls=2 \
    total=6.521s mean=3.260s min=3.180s max=3.342s
```

**Why this matters:** for `mclapply` / `multiprocessing.Pool` workloads
where each fork is short-lived (e.g. fgsea's worker calls < 50ms each),
**no profiler backend can see the work** — sample doesn't attach in time,
Rprof doesn't follow forks, Scalene's wrapper sees only parent. But the
override wrapper IS in-process to each worker, so its timing accumulates
in worker memory and the summary line emits before the worker exits.

`parsers.py` aggregates lines across workers (group by pid, take the last
cumulative snapshot per pid, sum across pids). Output:

```
[profile] Override timing (1 tracked):
  fgsea::fgseaMultilevel       calls=    16  total=  52.510s  mean=3281.875ms
                               [aggregated across 16 workers]
```

This is **the only deterministic, fork-safe signal** for autozyme's
canonical pattern (`install_override(target, fast_version)`). Use it
when the profiler hotspots show parent-side IPC noise.

The R `marker_fn` emits cumulatively per call (every call = a fresh
"snapshot" line) because `mclapply` workers terminate via `_exit()`,
which bypasses R's session-end hooks. The parser dedupes per-pid, so
this just adds redundancy not noise. Python `marker_wrapper` emits via
`atexit` (reliable for `multiprocessing.Pool`).

Custom override helpers should not invent a new log format. If the framework
`install_override()` cannot patch the target directly, wrap the custom call
with `with_override_timing("<pkg>::<fn>", { ... })` in R or
`with with_override_timing("pkg.fn"):` in Python. That emits the same
`[override active]` / `[override summary]` protocol. If a legacy custom
helper only emits `[override active]`, `zyme profile` records it in
`override_markers` and surfaces it as a marker-only actionable target, but
without timing.

## `--diff` — cross-iteration comparison

After accepting a patch and re-profiling, see what actually changed:

```bash
zyme profile --diff history:cpu_tiny_iter5 \
             --diff-against current
```

Resolves:
- `current` / `head` → latest `profile_history/<run-id>/profile.json`
- `history:<substring>` → most-recent matching entry under `profile_history/`
- otherwise → treat as a path

Output (text, or JSON via `--json`):

```
[diff] history:cpu_tiny  →  current
  history: backend=cpu tier=tiny  hypothesis='baseline'
  current: backend=cpu tier=tiny  hypothesis='[conservative] vectorized loop'
  wall: 8.234s → 5.122s (delta -3.112s (-37.8%))

[diff] Hotspots present in BOTH (sorted by B's pct):
  run.py:127:hot_loop          1→3   45.2% → 12.1%
  run.py:89:setup              2→1   18.0% → 28.4%

[diff] Disappeared from history (gone in current):
  - run.py:142:inner_op  (8.4% self)

[diff] Override timing changes:
  fast.fgseaMultilevel    calls=16→16  total=-12.343s (-23.5%)  mean=-0.771s (-23.5%)
```

**Cross-backend warning** — diffing `cpu` vs `full` triggers a notes
warning since the hotspot label sets are structurally different
(function-level cProfile vs line-level Scalene). The wall delta is
still meaningful but appeared/disappeared lists may just be backend
coverage differences, not real changes.

  "lang": "py" | "R",

  //
  // `layer_breakdown` and `per_layer_top` are the FIRST things the agent

**For agents:** start with `actionable_hotspots`. It promotes
`override_summary` entries ahead of profiler runtime/IPC noise, includes
marker-only `[override active]` entries when a custom helper cannot emit
timing, then falls back to raw profiler `hotspots`. `hotspots` remains the
unmodified profiler view. `call_chains` gives representative dynamic stacks
for backends that expose them, and `notes` documents backend caveats (idle
filter, native attribution warnings) — read these before drawing conclusions.

## Architecture

```
zyme/commands/profile/
├── __init__.py        # re-exports cmd_profile
├── command.py         # cmd_profile orchestration: arg dispatch → runner → parse
├── backends.py        # backend resolution + availability probing + scalene/memray args
├── parsers.py         # cProfile / Rprof / Scalene / memray → normalized hotspots
│                      # + extract_override_summaries() (cross-pid aggregation)
├── native.py          # macOS sample(1) wrapper: NativeSampler + sample-output parser
├── render.py          # evidence-card stderr formatting
├── archive.py         # profile_history/<run-id>/ directory writer
└── diff.py            # cmd_profile_diff: profile.json A vs B delta
```

Mechanism layer (in `helpers.{py,R}`, sourced by every task's pipeline):
- `with_profile()` — scoped target-region marker. For Python `cpu`, Python
  scoped `mem`, and Rprof backends it starts/stops the profiler around that
  block; for whole-process backends it remains a no-op/marker.
- `with_subprofile(name)` — manual annotation for sub-block timing
- `install_override()` — patches a function + records per-call timing
  + emits `[override summary]` line at exit (Python: atexit; R: per-call
  cumulative snapshot for fork survivability)

Runner integration (`runner.py`):
- `pipeline_python_args` — inserts wrapper args between python and `run.py`
  (Scalene `--memory --profile-system-libraries`, memray `run --native`)
- Python `mem` chooses scoped mode when `pipeline/run.py` calls
  `with_profile()`; otherwise it uses the external memray wrapper so legacy
  tasks still produce a profile.
- `side_observer` — for native backend: `attach(pid)` after Popen,
  `detach()` after pipeline exits (NativeSampler spawns sample(1) +
  watchdog for child PIDs via `pgrep -P` and process-group `pgrep -g`)
- `skip_evaluate` — profile is diagnostic, evaluate phase is skipped

## Performance characteristics

From `tests/bench_profile.py` reps=3, 8 fixtures (May 2026, M-series Mac):

| backend | overhead range | CV (variance) | comment                                |
|---------|---------------|---------------|----------------------------------------|
| `cpu`   | 0.96–1.42×    | <3%           | cProfile heaviest on tight Python loops|
| `full`  | 1.04–5.87×    | <6%           | Scalene heavy on Python loops, ~1× on R/profvis |
| `mem`   | 0.97–1.51×    | <5%           | memray well-engineered                 |
| `native`| 1.04–1.94×    | <12% (1 flaky)| macOS sample is kernel-supported       |

**Watch out for:**
- Scalene at 5–6× overhead on tight Python loops (`synthetic`, `alloc_heavy`).
  For tasks already ≥30s baseline, `full` is expensive — use `cpu` or
  `native` for routine profiling, `full` once for line-level diagnosis.
- Scalene SIGSEGVs on workloads that mix OpenMP heavily (e.g.
  astropy_lombscargle's pocketfft). When this happens, fall back to
  `native` (sample handles it cleanly).
- `native` on very-short-wall tasks (<500ms) may capture nothing — even with
  process-group polling and late attach, workers can exit before `sample(1)`
  produces its first interval. Use a longer tier or another backend.

## Known limitations

| Case | What happens | Workaround |
|------|--------------|------------|
| `mclapply` workers <50ms each | Profilers see parent IPC only (`unserialize`, `mcfork`, `lazyLoadDBfetch`) | **Use `override_summary`** — option 3 sees inside workers |
| Scalene + heavy OpenMP | SIGSEGV during run | `--backend native` |
| `xctrace` CLI on macOS 15 + Xcode 16 | Empty `.trace`, broken export | Don't try; sample(1) is the path |
| pure-Python single-process via `native` | Top frames are `_PyEval_EvalFrameDefault` etc. (Python interpreter) | This is honest — sample is symbol-aware not Python-frame-aware. Use `cpu` or `full` for Python function names. |
| R fast-fork via `native` | Child workers exit before sample's first interval (~1ms) — captures parent only | Same option 3 answer |
| Python multiprocessing.Pool | `override_summary` works (atexit fires), but workers' Scalene stdout doesn't always forward | One process at a time when full profile needed |

## Adding a new backend

For a hypothetical `--backend foo`:

1. **`helpers.{py,R}`** — add a branch in `with_profile()` if foo is in-process
   (writes `foo.out` next to `pipeline/`); skip if foo is external.
2. **`backends.py`** — add to `resolve()`. If optional, add availability
   probe via `_probe_python_pkg` / `_probe_r_pkg`. Decide fallback policy
   (`full` falls back to `cpu`, `mem`/`native` refuse — match the rule
   that fits foo's signal axis).
3. **`backends.py` (if external wrapper)** — add `foo_pipeline_args(out)`
   returning args to insert between python interpreter and `run.py`.
4. **`backends.py` (if observer like sample)** — add a class with
   `attach(pid)` / `detach()`; pass via `side_observer=` in `command.py`.
5. **`parsers.py`** — add `_parse_foo()` returning `(hotspots, notes)`
   matching the canonical schema. Wire into `normalize()`.
6. **`command.py`** — add the dispatch branch (set `extra_env` / wrapper
   args / observer).
7. **`cli.py`** — extend `--backend` choices + help text.
8. **Tests** — add to `tests/test_profile_fallback.py` (resolve unit test)
   + a fixture to `tests/bench_profile.py` `FIXTURES`.
9. **`templates/task_template/.gitignore`** — add foo's raw artifact path.

## Testing

Two layers:

**Unit/integration tests** (`pytest tests/`, ~140s):
```
test_profile_fallback.py    — backends.resolve() per-backend rules (12 tests, mocked)
test_profile_backcompat.py  — ZYME_PROFILE=1 zyme run still works (4 tests)
test_override_summary.py    — option 3: regex, cross-pid aggregation (12 tests)
test_bench_profile.py       — fast unit coverage for benchmark harness validation
test_profile_schema.py      — profile.json schema fields complete (10 tests, slow)
test_profile_archive.py     — profile_history/ behavior (4 tests, slow)
```

**Bench matrix** (`python tests/bench_profile.py`, ~20–30 min reps=3):
- 8 fixtures × 4 backends × 3 reps = 96 cells
- Per-cell: wall median, CV%, overhead vs baseline, hotspot recall,
  override-summary presence, schema validity
- Synthetic ground-truth (pure-Python A/B/C ratio fixture) catches
  parser ranking bugs early
- See `tests/bench_profile.py` `FIXTURES` for per-fixture spec

Run quick smoke:
```bash
python tests/bench_profile.py --reps 1 --fixtures synthetic
```

Run as an enforcing check:
```bash
python tests/bench_profile.py --reps 1 --fixtures synthetic --strict
```

`--strict` exits nonzero when a cell fails schema/hotspot/override checks,
exceeds its declared `max_overhead_x`, or is unstable (`CV > 20%`).

## Back-compat: `ZYME_PROFILE=1 zyme run`

The old path still works — `ZYME_PROFILE=1` with no `ZYME_PROFILE_BACKEND`
defaults to `cpu` (cProfile / Rprof). `with_profile()` becomes a no-op
when `ZYME_PROFILE` is unset, so committed pipeline code with
`with_profile()` blocks doesn't impose overhead on normal `zyme run`.

The new `zyme profile` subcommand is preferred:
- Auto-discoverable via `zyme --help`
- Backend selection via flag, not env-var-soup
- Skips evaluate (faster diagnostic)
- Auto-archives to `profile_history/`
- Surfaces `override_summary` (the env-var path also surfaces it, but
  there's no parser to consume it without going through `zyme profile`)

The runner doesn't gate on which path the user chose — both paths feed
through the same `helpers.with_profile()` dispatch.
