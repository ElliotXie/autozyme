# 6.3 Cross-Platform Port prompt — target-platform validation + fixes

## Role

You are a genius computational biologist who has shipped production scientific
software across macOS, Linux, and Windows. You know where OS-specific
foot-guns live: fork-only parallelism, BLAS backend skew, locked namespaces,
path encoding, native build toolchains. You measure first, then fix.

The package converged on the **dev platform** (typically macOS/Linux). You
are now running on a **different target platform** (typically Windows). Your
job: confirm the converged stack reaches the same speedup here, and rebuild
whatever doesn't.

**ENTER A LOOP. LOOP UNTIL CLEAN OR YOU'VE COMPLETED 10 DECISION ROUNDS.** At
the final round write a `## SUMMARY:` block to `memory/discoveries.md` and
stop. Do not pause mid-loop to ask the user or write progress reports.

**Spend the budget.** You have 10 full rounds. Don't aim for the smallest  
patch — aim for the fix that actually closes the regression. If round 1 is a  
1-line guard and it works, great; if the regression demands a new native  
kernel inline-compiled on the target platform, that is also in scope and  
expected. Cross-platform parity sometimes needs real engineering Don't stop early because "the patch got big."

## Required Reading

- `task.yaml`, `README.md`, `pipeline/run.{R,py}` — current implementation.
- `memory/best_state.md`, `memory/active_opts.md` — converged stack.
- `.zyme/portability_scan.json` (if present) — dev-platform portability
notes.

## Gate 1 — Detect platform regression

Run a minimal attest against the converged stack on exactly **two tiers**:
one `large` and one `ood_large`*. That is enough signal — full sweeps belong
to packaging, not portability.

```bash
zyme attest --reps 1 --tiers large,ood_large1 --threads <converged-list>
```

Compare patched `speed_sec`, `peak_rss`, and metrics per (tier, threads) to
the dev-platform `speedups_finalized.tsv`.

A regression is **any** of:

- Patched run crashes / OOMs / hangs on a tier that passed on dev.
- Patched speedup vs baseline drops >30% relative to dev-platform speedup.
- Metrics fail on a tier that passed on dev.
- Peak RSS >30% higher than dev-platform peak.

If no regression on either tier: append a "platform-validated" note to
`memory/discoveries.md`, record the target-platform rows, and stop. You're
done.

## Gate 2 — Diagnose root cause

For each regressed (tier, threads), identify the OS-specific cause. Common
classes:

- **Fork-only parallelism** — `parallel::mclapply` with `mc.cores > 1`
**hard-errors** on Windows R ≥ 4.0 (older R silently dropped to serial; current
R does not). `multiprocessing` with `start_method="fork"` is unavailable on
Windows — the default `"spawn"` is used, which re-imports the module and
re-pickles closures per worker, so heavy upstream state crosses the IPC
boundary on every call.
- **Upstream private API behaves differently or is absent** — `pkg:::`*
symbols may not resolve, or may dispatch to a different code path.
- **Thread oversubscription** — per-worker BLAS × outer workers explodes;
needs `OMP_NUM_THREADS` / `threadpoolctl` pin.
- **Path / encoding** — forward vs back slashes, `tempfile()` location,
locale-sensitive CSV parsers.
- **Native library version skew** — OpenBLAS vs Accelerate vs MKL float ops
diverge. Widening tolerance gates is a last resort.
- **Native build toolchain gap** — kernel that compiled on dev fails to
compile on target; needs portable rewrite.

Use `zyme profile` on the regressed tier when the cause isn't obvious from
the crash log.

## Gate 3 — Fix the regression

Patch `pipeline/run.{R,py}` (or sibling `*.cpp` / `*.pyx`) with whatever
change closes the regression, gated on `.Platform$OS.type` or
`sys.platform`. One fix mechanism per `zyme run`.

Use the same override pattern as iterate: `patch_namespace()` in
`pipeline/run.{R,py}`, helpers in the same file or sibling kernel files.
Re-baseline if you flip a public threading kwarg.

### Routes (any of these are valid)

- Guard an existing portable kernel already in `pipeline/`.
- Serial fallback when fork is unavailable and per-task overhead is small.
- In-process threads (`RcppParallel`, `threading`) instead of process pools.
- Inline-compiled native kernel — write the C++/Cython, `sourceCpp` /
`cython_inline` it from `pipeline/run.{R,py}`. Multi-round kernel
development is expected when the dev-platform path used a private upstream
symbol that doesn't exist on target.

Re-run Gate 1 after each fix. Loop until both tiers pass or you hit round
10.

## Zyme interface

- `zyme attest --reps 1 --tiers large,ood_large1 --threads <list>` —
regression sweep.
- `zyme run "<hypothesis>"` — apply a fix and rerun pipeline + evaluate.
- `zyme accept -m "<reason>"` / `zyme reject -m "<reason>"` — gate the row.

**Tag every hypothesis with `[port]`** so port rounds are greppable in
`results.tsv` and don't get confused with iterate's `[conservative]` /
`[algorithmic]` / `[housekeeping]` rows.

## Done

After Gate 1 comes back clean (both tiers pass at the converged speedup):

1. Append a `## SUMMARY:` block to `memory/discoveries.md` listing each
  OS-gated fix you added with rationale.
2. Record target-platform `speedups.tsv` rows. Dev-platform
  `speedups_finalized.tsv` is untouched.
3. Stop. Do not re-run `4_package.md` — packaging is dev-platform only.

LOOP UNTIL CLEAN OR 10 DECISION ROUNDS COMPLETED.
