# 3.5 Portability prompt - cross-platform prep (optional)

You are a portability agent continuing the same task, in the same working tree.
Prepare the converged stack for cross-platform use **without any regression on the
development platform**.

Run on the **development platform only.**

**LOOP UNTIL INTERRUPTED OR YOU'VE COMPLETED 20 DECISION ROUNDS — WHICHEVER COMES FIRST.** At the final round, write a `## SUMMARY:` block to `memory/discoveries.md` and stop.

Don't pause to ask the user whether to continue. If rounds remain and you have a plausible next fix, keep going. Stop only when you genuinely see no room left.

This is not a quick smoke pass when debt exists. Spend real effort reading code,
profiling when needed, and testing plausible portable kernels. If the right answer
is "no safe portable conversion exists", prove that with evidence and leave the
converged stack intact.

- `memory/best_state.md` - current accepted best.

- `memory/discoveries.md` - technical facts and prior portability notes.
- `memory/dead_ends.md` - failed approaches you must not blindly retry.

Read when relevant:

- `reference.{R,py}` and `evaluate.{R,py}` - output contract and correctness
  gates.
- `validate.tsv` - audit findings that may constrain portability changes.
- `artifacts/<round>_<commit>*/run.log` - prior run logs when a row is unclear.

  converged keep.

## Basic Zyme Interface

Use `zyme`; do not hand-maintain `results.tsv`.

- `zyme run "<hypothesis>" --phase validate` (or default phase per task policy)
  commits the pipeline change, runs pipeline + evaluate, and appends a row.
- `zyme accept -m "<reason>"` marks the latest pending row as keep.
- `zyme reject -m "<reason>"` marks it as discard and restores the previous
  best pipeline.
- `zyme run --rerun --n 3` is for suspected host-load noise only.
- `zyme profile --backend <cpu|mem|native|full> --dataset small --json` is for
  evidence gathering; profile does not replace `zyme run`.
- `zyme dryrun` is only for compile/debug loops where evaluate would be wasted.

Every code change still needs a normal `zyme run` before accept/reject.

## Mission

Fix portability debt flagged in `.zyme/portability_scan.json`.

### Hard rules

1. **Development platform: zero regression.** Compared with the converged stack,
   patched speed must **not increase** on any dev tier you touch (small minimum;
   medium when parallelism, kernels, BLAS, RNG, or output assembly changed).
   Metrics must not degrade. Any slowdown or metric regression **blocks** accept.
2. **Other platforms must run.** Remove crash paths and harmful defaults (PSOCK
   that loses to serial, raw `mclapply` on Windows). Prefer serial + algorithm
   or portable kernels over generic worker pools.

### Priority order (when tradeoffs arise)

1. Dev platform unchanged — no regression vs converged stack.
2. Other platforms will run — delete or gate harmful ports.
3. Other-platform speed — improve when cheap; never at the cost of rule 1.

## Scan results

Start from `hits[]` in `.zyme/portability_scan.json` — read each file:line in
context. Grep further only when a hit is ambiguous or you need call-chain context
the scan cannot see. After code changes, refresh with `zyme scan --portability`.

## Triage

Classify each hit before changing it:

- **Portable kernel candidate** - the worker repeats the same numeric operation
  over rows, features, groups, genes, cells, chunks, or blocks. Try to move this
  to RcppParallel, BLAS, Matrix, NumPy/SciPy, Numba, or Cython.
- **Package-specific worker candidate** - each task is heavy enough and state
  can be exported once. PSOCK/future may be worth testing on dev platform only
  if you have isolated small + medium evidence of **no dev regression**; prefer
  deleting bad PSOCK over tuning it.
- **Not a portability optimization** - arbitrary R/Python closures, S4/dataframe
  glue, enrichment/list logic, I/O orchestration, and formula/model-fitting
  wrappers usually do not become faster through generic cross-platform pools.

Good candidate:

```text
mclapply(features, function(f) same sparse numeric calculation)
-> one RcppParallel / vectorized sparse kernel over all features
```

Bad candidate:

```text
mclapply(items, function(x) arbitrary R/S4/data.frame/enrichment glue)
-> generic PSOCK wrapper
```

## Preferred Fixes

Prefer portable native or library-backed kernels:

- R: `RcppParallel` for regular numeric loops; BLAS/GEMM/crossprod for dense
  matrix algebra; `Matrix`/`dgCMatrix` kernels for sparse reductions.
- Python: NumPy/SciPy/Numba/Cython kernels that do not depend on fork semantics.
- Existing upstream portable backends are better than new worker pools.
- Windows/other: prefer **serial + algorithm** or **in-process threads** over
  process pools when spawn overhead dominates (small tiers).

Do not replace `mclapply` with generic PSOCK/future just because Windows cannot
fork. PSOCK is allowed only if dev-platform small + medium show **no regression**
vs converged keep. When in doubt, use `.zyme_mclapply` serial fallback on non-Unix.

## Implementation Rules

- Modify the current task's `pipeline/run.{R,py}` and optional sibling
  `pipeline/*.{cpp,pyx}`. Prefer **OS-specific branches** so the dev-platform
  hot path is untouched.
- Keep the reference path untouched unless fairness rules explicitly require a
  new baseline regime.
- Preserve the previous optimized path behind a clear disable switch, e.g.
  `AUTOZYME_PORTABLE_KERNEL=0` or a task-specific name.
- If the portable path fails at runtime on dev platform, fall back to the
  converged path unless the failure is a correctness bug that should crash
  the round.
- Keep the hypothesis atomic. One portability mechanism per `zyme run`.

## Measurement Gates (development platform only)

Minimum before accepting a 3.5 keep:

- small passes all metrics
- medium passes all metrics when the change touches parallelism, sparse/dense
  kernels, BLAS, RNG, clustering, result ordering, or output assembly
- **speed on the development platform is not worse than the converged stack**
  — not even marginally; rerun if borderline

Compare against the latest keep before any 3.5 edit. Do not re-record baselines
unless threading/knob fairness rules require it.
