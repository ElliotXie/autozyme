# Transfer-init — autozyme-framework

You are the **transfer-init agent**. A sibling task has converged; you initialize a new task that inherits its applicable code and knowledge, so the next iterate session starts on top of source's gains rather than at upstream stock.

You **replace `1_init.md`** for this task — both init duties and transfer duties are yours. You run **once**, in a freshly-scaffolded target directory (`bin/zyme init` has copied the template + initialized git, nothing else). After you finish, the user spawns `2_iterate.md` and the task looks structurally identical to any other zyme task plus one extra `memory/transfer_knowledge.md`.

## Why a sibling

The two tasks share an upstream package and share enough of the call chain that source's converged pipeline already carries optimizations the target will execute. Example: source ran `infercnv::run(HMM=FALSE)`, target runs `infercnv::run(HMM=TRUE)` — steps 1–15 are identical and source already optimized them; target's iterate only needs to attack the new HMM steps 17–20 on top.

If source's optimized surface only marginally overlaps with target's call chain, stop and tell the user — fresh `1_init.md` is cleaner than transfer with little to inherit.

## Memory layout — native vs inherited

You introduce one new file; the rest follow standard convention:

- **`memory/transfer_knowledge.md`** (NEW; you write this) — single file capturing everything inherited from source: which opts are baked into the starting pipeline, filtered discoveries, filtered dead_ends, config deltas to watch. Iterate READS this; iterate doesn't write to it.
- **`memory/discoveries.md`, `memory/dead_ends.md`** — leave at template stub. These are iterate's NATIVE journal going forward. Keeping native and inherited in separate files prevents inherited entries from getting re-summarized / re-tagged out of recognition over many rounds.
- **`memory/active_opts.md`** — populate with source's live stack tagged `[inherited]`. This file is a state mirror of `best`'s composition; at handoff `best`'s composition IS source's stack.

## Your steps, in order

**1. Read source end-to-end.** `task.yaml`, `README.md`, `family.md`, `pipeline/run.{py,R}` (at source's `best` SHA — `git -C <source> show <best>:pipeline/run.{py,R}`), `memory/discoveries.md`, `memory/dead_ends.md`, `memory/active_opts.md`, last 30 rows of `results.tsv` for context. Record source's best SHA short for provenance — you'll cite it everywhere.

**2. Cross-check call chains.** Read source's README's call chain section + sketch target's mentally from upstream source (target's config differs from source's — figure out which steps run, which don't, which differ). If overlap is too thin to justify transfer, stop here and route the user back to `1_init.md`.

**3. Set up target's reference / evaluate / task.yaml — informed by source.** Init duties, but you have source as a reference point:
- **`reference.{py,R}`**: stock upstream call with target's config. Usually differs from source's in the config args (e.g. `HMM=TRUE` vs `HMM=FALSE`); the surrounding setup is the same.
- **`evaluate.{py,R}`**: start from source's, then add/modify metrics for any output target produces that source doesn't (e.g. HMM emits discrete state calls — add ARI / agreement metric on those).
- **`task.yaml` metrics + thresholds**: copy source's thresholds for shared metrics (source's experience is calibrated on this data); add new metric rows for new outputs.
- **`task.yaml` datasets**: default = inherit source's tier choices verbatim. `data/` → symlink to `<source>/data/` unless target needs a different domain (rare for true siblings).
- **`upstream_repo/`** → symlink to `<source>/upstream_repo/` if same repo + commit; otherwise clone fresh and record the new SHA in README.
- **`executor:` block**: copy from source verbatim if same language/env.

**4. Place the inherited pipeline.** Copy source's `pipeline/run.{py,R}` at source's `best` SHA over target's stock copy. Reconcile only what must change for target's contract:
- Env vars (`ZYME_DATA_PATH` / `ZYME_REFERENCE_DIR`) — should already be correct.
- Output schema — must match target's `evaluate` (may differ from source's). Adjust save path / file format if needed; do not change algorithmic logic.

**5. Measure upstream baseline at all three tiers + `record-baseline` each.** Same protocol as `1_init.md` steps 5/5b. Crucial: the baseline is `reference.{py,R}` (upstream stock with target's config), NOT the inherited pipeline. speedup_pct must anchor to upstream so it captures both inherited and future native gains honestly. Validate each tier hits its band (~1 / ~3 / ~6 min); swap dataset if not.

**6. Sanity-check the inherited pipeline at each tier.** Run `pipeline/run.{py,R}` against each tier's `reference_outputs/<tier>/` via `evaluate.{py,R}`. Shared metrics should pass thresholds (source already validated). For NEW metrics target added in step 3, this is the first time they're measured against the inherited pipeline — if any fail, that's an algorithmic decision (does the inherited opt break target's stricter contract, or is the new threshold wrong?); flag to the user, don't auto-fix.

**7. Profile the inherited pipeline on small.** This surfaces what's LEFT after source's opts — which is what target's iterate should attack. Don't profile the stock pipeline (irrelevant; nobody runs it after round-0). Standard helper: `ZYME_PROFILE=1 ...`. Lift top hot-spots into README's "New angles" section in step 9, then delete profile artifacts.

**8. Write `memory/transfer_knowledge.md`.** Structure:

```markdown

Transferred YYYY-MM-DD. Source converged after N rounds; best speedup vs upstream = Mx on tier T.

- <opt 2>: ...

## Skipped (deliberately not ported)
- <opt or angle>: <reason — e.g. "rewrote step 8; target's config bypasses step 8">

## Inherited discoveries
[Filter source/memory/discoveries.md. Port entries about machinery target executes.
Verbatim copy with `[from <source_task>]` suffix on each heading.]

## Inherited dead ends (with caveats)
[Filter source/memory/dead_ends.md MORE conservatively — angles that flopped under
```

## Constraints

- Don't touch source's files. Source is frozen at its best; you only read.
- Don't commit the inherited pipeline. Leave it in target's working tree; iterate's first `zyme run` commits it as round 1 with description like "inherited from <source>@<sha>: <opts>", keeping the attempts chain readable from round 1 onward.
- Don't optimize anything in target's pipeline beyond what's inherited. New optimizations are iterate's job.
- Don't import source's `results.tsv` rows. speedup_pct anchors don't transfer across tasks.
- Don't write to source's `family.md` directly — surface the update as a chat ask in step 10.
- Don't profile target's stock pipeline. Stock is reference; nobody runs it after round-0.

## Output requirements

When you finish, the target directory satisfies all of `1_init.md`'s output requirements (3-tier datasets, reference/evaluate/pipeline filled, `reference_outputs/<tier>/` populated, sanity check passes shared metrics, 3 baselines persisted via `record-baseline`) PLUS:

- `memory/transfer_knowledge.md` exists, non-empty, follows the schema in step 8
- `memory/active_opts.md` carries source's stack tagged `[inherited]`
- `memory/discoveries.md` / `memory/dead_ends.md` remain at template stub (empty native journal)
- `pipeline/run.{py,R}` is source's converged copy at source's `best` SHA (uncommitted, in working tree)
- README's Anticipated angles section has both `Inherited` and `New angles` subsections
- `family.md` exists with target's own scope verdict + post-hoc back-pointer to source

These are correctness requirements — `6.2_iterate.md` depends on them.
